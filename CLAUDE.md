# CLAUDE.md — StudyAssist Project Context

## Technology Stack

| Technology | Version | Why This Choice |
|---|---|---|
| ASP.NET Core | 10.0 | Target platform; .NET 10 for performance improvements and minimal API features |
| PostgreSQL + EF Core + Npgsql | 10.* | Relational data with migrations; PostgreSQL's `ON CONFLICT DO UPDATE` is required for atomic rate-limit upserts that EF Core cannot express |
| ASP.NET Identity | 10.* | PBKDF2 password hashing, password validation rules, and direct password change without reinventing them |
| MailKit | 4.* | SMTP email delivery for password reset codes |
| JWT Bearer (HS256) | 10.* / 8.* | Stateless auth with revocable refresh tokens; HS256 is sufficient for a single-server trust boundary |
| OllamaSharp | 5.4.24 | Local LLM inference — keeps student data on-premises; has native streaming support. `Llm:OllamaModel` is pinned to `todorov/bggpt`, a Bulgarian-specialized text model, chosen after `minicpm-v` proved unreliable for Bulgarian text generation (see Language Policy's known gaps below). `Llm:OllamaVisionModel` stays pinned to `minicpm-v` since BgGPT is text-only and `minicpm-v` remains the only multimodal model kept pulled locally, used solely by `OCRService`'s scanned-PDF fallback — check `ollama list` before repointing either config value at an unpulled model name |
| ZhipuAI (HTTP) | — | Alternate `IChatService` implementation (`ZhipuAIChatService`) calling ZhipuAI's OpenAI-compatible API (`/v4/chat/completions`); **not currently wired** — `Program.cs` registers `OllamaChatService` as `IChatService` and there is no automatic runtime failover, so switching backends means editing that DI registration |
| Qdrant | 1.17.0 (client) | Vector DB for RAG; supports payload-based metadata filtering so grade-N students only receive grade ≤ N curriculum material. `1.17.0` pins the `Qdrant.Client` NuGet package — the server image in `docker-compose.yml` (`qdrant/qdrant`) has no version tag and pulls `:latest`, so the server itself isn't pinned |
| nomic-embed-text-v2-moe (Ollama) | — | 768-dim embeddings; dimension is hardcoded in `EmbeddingService.cs` and must match the Qdrant collection. `Llm:OllamaEmbedModel` switched from `nomic-embed-text` v1.5 to this multilingual MoE release on 2026-08-27, after a retrieval audit found two compounding issues with the old setup: (1) queries/chunks were embedded with no `search_query:`/`search_document:` task-instruction prefix, which both models are trained to expect; (2) v1.5 is English-focused per its own model card, while this app's corpus and queries are Bulgarian. A hand-authored 20-question fixture (`TestData/RetrievalFixtures/grade10-math-v1.json`), measured against the real ~920-chunk production corpus rather than a small decoy pool, showed prefixing the *unchanged* v1.5 model alone gave no real improvement (if anything, slightly worse: 1/20 vs. 3/20 baseline top-3 hits) — the win came from the model swap itself. Verified end-to-end post-migration against the real, now-live `studyassist` collection: **3/20 → 13/20** questions with the correct chunk in the top 3 (see "Retrieval Quality" below for full methodology and known residual gaps). `EmbeddingService.GetDocumentEmbeddingsAsync`/`GetQueryEmbeddingsAsync` apply the respective prefix automatically. |
| UglyToad.PdfPig | 1.7.0-custom-5 | Fast plain-text extraction from machine-readable PDFs (primary OCR path) |
| PDFtoImage + Tesseract | 5.2.0 | Fallback OCR for image-heavy or scanned PDFs |
| Pix2Text (Docker, :8503) | — | Math OCR producing LaTeX output — required because Bulgarian math textbooks contain dense formula notation. `pix2text_server.py`'s `is_suspect_formula` filter and `PDFLoader.GetPageImages`' render DPI (bumped to 200, scoped to only the formula-OCR call site) were both fixed 2026-08-31 after a garbled-Cyrillic-and-truncated-LaTeX corruption issue was traced to this pipeline — see "Retrieval Quality" below |
| SkiaSharp | 3.119.2 | Image manipulation in the OCR pipeline; macOS native assets are included because dev happens on Mac |
| LanguageDetection.NETStandard | 1.3.1 | Offline n-gram language identification (`Services/LanguageDetectionService.cs`) so prompts can tell the LLM explicitly which language to respond in, rather than relying on `minicpm-v` to infer it from a soft instruction — the instruction-only approach was unreliable, especially for short exam topics. Cyrillic input is always treated as Bulgarian directly (reliable at any length); non-Cyrillic detection is only trusted on real sentences — bare topic phrases like "Algebra" are misdetected by the n-gram model with high confidence, so `ExamService` gates on `requireStrongSignal: true` (≥4 words) before trusting a non-Cyrillic result |
| Vue 3 + Vite + TypeScript | 3.* / 8.* / 6.* | Frontend framework (`frontend/`), scaffolded via `npm create vite@latest frontend -- --template vue-ts`; chosen over React per project decision |
| Pinia | 4.* | Frontend state management — auth state (JWT, refresh token, user, role) needs to be read from many unrelated places (router guards, every API call, future stores) |
| vue-router | 4.* | Frontend routing; `beforeEach` guard redirects unauthenticated requests to `/login` and enforces per-role `meta.roles` on the four `/app/{role}` home routes |
| @fontsource/fredoka, @fontsource/nunito | 5.* | Self-hosted fonts matching the hand-designed mockup (`Fredoka` for headings, `Nunito` for body) — no external Google Fonts network call at runtime |

  EmbeddingService.cs    Text → 768-dim vector via Ollama nomic-embed-text-v2-moe; `GetDocumentEmbeddingsAsync`/`GetQueryEmbeddingsAsync` are the production entry points, applying the `search_document: `/`search_query: ` task-instruction prefix (public `DocumentPrefix`/`QueryPrefix` constants) the model expects — the underlying `GetEmbeddingsAsync` stays prefix-agnostic since `RetrievalDiagnostics`/`RetrievalComparisonRunner` need to apply prefixes selectively to compare configs
  QdrantService.cs       Vector DB CRUD (upsert, search with grade filter, delete by file); each chunk's payload includes a 1-indexed `page` field (`ChunkData.PageNumber` / `SearchResult.Page`) recording its source PDF page, so a retrieved chunk can be traced back to its exact page — `SearchAsync` reads it with a guarded fallback to `0` for any point upserted before this field existed
  RetrievalDiagnostics.cs CLI-only diagnostic tool (`dotnet run -- diagnose-retrieval "<question>" <grade> [--prefix]`) that reproduces `RAGService.GetContextAsync`'s embedding/search behavior and prints ranked Qdrant results — score, subject, grade, page, source file, text preview — against the current 0.1 minScore threshold, so retrieval quality can be inspected without the threshold hiding what's actually being retrieved; the optional `--prefix` flag embeds the question with `EmbeddingService.QueryPrefix` for a quick single-query before/after comparison; must not be wired to any HTTP endpoint, same CLI-only rule as `VisualisationService`
  ChunkSampler.cs        CLI-only, READ-ONLY tool for browsing the production `"studyassist"` Qdrant collection (Scroll/Retrieve only — never Upsert/Delete). `dotnet run -- sample-chunks <grade> [sourceFile] [limit]` previews chunk id/page/subject/text; `dotnet run -- show-chunk <pointId>` prints one chunk's full untruncated text; `dotnet run -- validate-fixture <fixturePath>` resolves every `ExpectedChunk` in a `RetrievalFixtureModels.cs` fixture and reports OK/MISSING, catching stale `matchText` before a comparison run. `ResolveChunkAsync` (find one chunk by sourceFile+page+matchText-substring) and `GetAllChunksForGradeAsync` (full read-only scan of a grade) are shared helpers reused by `RetrievalComparisonRunner.cs`
  RetrievalFixtureModels.cs POCOs (`RetrievalFixture` / `FixtureQuestion` / `ExpectedChunk`) for the JSON retrieval-regression fixture format under `TestData/RetrievalFixtures/`. Expected chunks are identified by `(sourceFile, page, matchText)`, never a raw Qdrant point id — `UpsertChunksAsync` mints a fresh GUID per point on every `reingest-grade`, so an id-pinned fixture would break on the next re-ingest
  RetrievalComparisonRunner.cs CLI-only (`dotnet run -- compare-retrieval <fixturePath> [--full-corpus] [--current-prefix]`) — evaluates a fixture against 3 embedding configs (current production / prefixed same-model / prefixed + `nomic-embed-text-v2-moe`) and prints per-question rank/score/top-3-hit plus an aggregate table. Configs 2/3 build disposable temp Qdrant collections via a raw `QdrantClient` (never `QdrantService`, never the production collection name), always torn down in a `finally` block; `--full-corpus` re-embeds the grade's *entire* corpus instead of just the fixture's own chunks (avoids a small-decoy-pool hit-rate confound — preserves original production point ids in this mode so `FindRank` can match by exact id rather than a fuzzy sourceFile+page+text-contains check, though see the code comment on a known limitation with byte-identical duplicate chunks); `--current-prefix` embeds Config 1's query with the prefix, letting the same tool double as a post-migration acceptance check directly against the real, now-migrated production collection
  PDFLoader.cs           PDF → text extraction (static utility). `LoadText` (PdfPig plain text), `LoadTextWithOcrAsync` (vision-OCR fallback), `LoadTextWithMathOcrAsync` (unused), and `LoadTextWithSelectiveFormulaOcrAsync` — the path ingestion actually uses: PdfPig plain text per page by default, plus a Pix2Text formula-only pass appended after a page's prose when that page embeds classic MathType/Equation-Editor fonts — all return `List<PageText>` (one entry per page, 1-indexed) rather than a single joined string, so page identity survives extraction. `CleanText` (whitespace/hyphenation/page-number-line cleanup) and `ChunkText` (paragraph/sentence-aware ~400-char chunking with 1-sentence overlap) remain pure single-string functions. `ChunkText`'s private `GetLastSentences` (the overlap helper) was fixed 2026-08-31: when `SplitSentences` finds no real sentence boundary in a flushed chunk — common in this corpus's dense OCR'd math text, where periods are rarely followed by a space — it used to fall back to reusing the *entire* chunk as "1-sentence" overlap, which self-perpetuated that chunk's leading text into every following chunk split from the same oversized paragraph (root cause of a duplicate-chunk issue previously misdiagnosed as stale ingestion data — see "Retrieval Quality" below). It now falls back to a short, character-capped tail (`OverlapFallbackMaxChars = 80`) instead of the whole chunk. `ChunkPages` is the page-aware entry point ingestion calls: it runs `CleanText`+`ChunkText` once per page, so a chunk can never span two pages and overlap (scoped to a single `ChunkText` call) can never pull in a neighboring page's text; pages under 20 cleaned characters — a blank divider page, or a page whose only text was a bare page number (`CleanText` already reduces either to 0 chars) — are skipped rather than merged into a neighbor, and the skip is logged so it's visible during ingestion. This closes a previously-disclosed gap where a chunk could span the end of one page and the start of the next, occasionally pairing a page's Pix2Text formula block with an unrelated adjacent page's prose.

  MathOcrService.cs      Calls the local Pix2Text HTTP server (:8503) to OCR page images into text + LaTeX (primary math OCR path)
  PersistentVectorStore.cs JSON-file-backed in-memory vector store with cosine-similarity search — legacy/local alternative to Qdrant

## Coding Conventions

### Naming
- Classes, interfaces, methods, properties: `PascalCase`
- Interfaces: `I` prefix — `IChatService`, `IUserRepository`
- Private fields: `_camelCase` with underscore prefix
- URL segments: `kebab-case` — `/api/auth/forgot-password`
- Database columns: `snake_case`, configured in `AppDbContext.OnModelCreating`

### Async Style
- All I/O (database, LLM, HTTP, file system) is `async Task<T>` / `async Task`
- Never use `.Result` or `.Wait()` — deadlock risk in ASP.NET Core's sync context
- Singletons that need DB access use `IDbContextFactory<AppDbContext>` — never inject `AppDbContext` directly into a singleton

### Error Handling
- Services return result tuples or error lists — they do not throw exceptions for expected failures
- Controllers own HTTP status codes; services own validation logic
- LLM and OCR calls use silent fallback (catch, log, return empty/unknown) — a failed AI call must never crash the HTTP request
- Startup validation is fail-fast: missing or placeholder config values throw before the app starts

### Response Format
- Single error: `{ "error": "message" }`
- Multiple errors: `{ "errors": ["...", "..."] }`
- User object: always `{ id, username, email, fullName, role, grade }` — no full ApplicationUser serialisation

## Library Choices

### Explicitly Prohibited
- `.Result` / `.Wait()` on async calls — deadlock risk
- Raw ADO.NET (SqlConnection, SqlCommand) anywhere except `RateLimiter.cs` where PostgreSQL `ON CONFLICT` atomicity is required
- Dapper or any ORM other than EF Core
- Swagger / OpenAPI packages — not in scope for this project

### Allowed but Scoped
- Raw `SqlQuery<T>` and `ExecuteSql` are used **only** in `RateLimiter.cs` for atomic upserts that EF Core's LINQ cannot express; keep them there

## Layer Rules

- **No SQL in controllers** — controllers call services and translate results to HTTP responses
- **No user DB access outside `IUserRepository`** — all `UserManager<ApplicationUser>` usage lives in `UserRepository.cs`
- **No auth logic in controllers** — `AuthService.cs` owns login, registration, token lifecycle; `AuthController.cs` only wires requests to the service and returns status codes
- **Rate limiting checks must come before auth service calls** — check `RateLimiter` before attempting any DB lookup in login/register/reset flows
- **No chat or LLM calls in controllers** — controllers stream or return results from `RAGService` / `IChatService`
- **Global admin HTTP endpoints require `Admin` role** — `GlobalAdminController` is backed by `AdminUserService` and restricted to the `Admin` JWT claim; `SchoolAdmin` users receive 403
- **SchoolAdmin endpoints must verify school membership** — always confirm the target user (student or teacher being operated on) belongs to the caller's school by comparing `SchoolId` integers; never trust a userId route parameter without a school-ownership check; never accept a school name string from the client — look up `SchoolId` from the authenticated user's record
- **School identity is always an int FK** — `ApplicationUser.SchoolId`, `Class.SchoolId`, `Subject.SchoolId` are all `int?`/`int` FKs to the `Schools` table; request DTOs that target a school use `int SchoolId`, not `string School`

## Security Requirements

- JWT secret must be ≥ 32 characters; enforced at startup before the app accepts connections
- Sensitive string comparisons (teacher registration code, class join code) must use `CryptographicOperations.FixedTimeEquals` — never `string ==`
- Teacher registration is gated by a per-school code (`SchoolTeacherCode`), generated/regenerated by that school's `SchoolAdmin` via `GET/POST /api/admin/teacher-code[/regenerate]`; regenerating invalidates the previous code immediately (soft-invalidated via `IsActive`/`RevokedAt`, not deleted). `AuthService.ResolveTeacherRegistrationAsync` matches the supplied code against all active codes with `FixedTimeEquals` and resolves `SchoolId` from the matched row — a teacher registration's `SchoolId` is **always** derived from the matched code, never trusted from the client's `SchoolId` request field. There is no global fallback code anymore (the old single `TeacherRegistrationCode` config value was removed); a school must have generated a code before any teacher can self-register into it.
- Student attachment to a class (and transitively a school) is gated by a per-class code (`ClassJoinCode`), generated/regenerated by that class's teacher via `GET/POST /api/teacher/classes/{classId}/join-code[/regenerate]` — same `FixedTimeEquals`/soft-invalidate pattern as `SchoolTeacherCode`, but lower-stakes (an org-affiliation, not a role elevation), so it's intentionally a separate model/table from the teacher code with its own regenerate cycle rather than reusing it. The code is **optional** everywhere it's accepted — `AuthService.ResolveClassJoinCodeAsync` treats an empty code as success-with-no-class (a student may always register/stay schoolless), but a non-empty code that matches nothing is a `400`, never a silent no-op. `ClassId`/`SchoolId` are always derived from the matched code, never trusted from the client. A student may join more than one class (`ClassStudent` join table, not a single `ClassId` FK), but all of a student's classes must belong to the same school — `AuthService.JoinClassAsync` rejects a code whose class belongs to a different school than the one the student is already attached to; the first join (registration or a later self-service join) is what sets that school.
- Password reset uses a DB-stored 6-digit code (10-min expiry) sent via email through `IEmailService` / `SmtpEmailService`; the code is never returned in the HTTP response. The `forgot-password` endpoint returns `404` when the email is not registered (enumeration protection is intentionally removed for this endpoint)
- Reset code verification and password reset share a per-email brute-force counter (max 5 attempts); issuing a new code clears the counter
- Rate limiting must remain database-backed — do not replace with `IMemoryCache` or `IDistributedCache`
- Rate limiting covers: login (per-account + per-IP), registration (per-email), password reset request (per-email, 5-min cooldown), reset code attempts (per-email, max 5), token refresh and logout (per-IP via `IsGeneralApiThrottled`)
- CORS allowed origins come from `Cors:AllowedOrigins` config — never hardcode `*` or specific URLs in code; allowed headers are restricted to `Content-Type` and `Authorization` only
- Refresh token exchange **and** revocation must both use `IsolationLevel.RepeatableRead` — do not lower this isolation level
- `appsettings.Local.json` contains real secrets for local dev — never commit it; production uses environment variables
- All user-supplied strings that reach LLM prompts must be passed through `InputSanitizer.SanitizeUserInput()` before interpolation — enforced in `RAGService.Ask()`, `ExamService.GenerateExamAsync()`, `ChatLogService.cs`, `ChatSessionService.cs`, and `PracticeQuestionService.cs`
- `RAGService` must be registered as **Scoped**, never Singleton — `_currentGrade` and `_temporaryChunks` are per-user instance state; in web endpoints, grade must come from the authenticated user's JWT claims, never from request parameters
- `VisualisationService` is CLI-only — it calls `Process.Start()` and holds static state; it must not be wired to any HTTP endpoint
- In production, `app.UseForwardedHeaders()` must run first in the pipeline and `KnownProxies` must list your specific proxy IPs — the current config trusts all proxies (safe for local dev, not for production)

## Language Policy

- **App UI target language is English.** This is the direction going forward, not a one-off exception — the redesigned auth screens (`LoginView.vue`/`RegisterView.vue`/`ForgotPasswordView.vue`) and the per-role dashboard screens (`StudentHomeView.vue` and friends) are in English for this reason. Any remaining Bulgarian UI strings elsewhere predate this decision and haven't been migrated yet; don't copy their language when building new screens.
- **The AI tutor must respond in whatever language the student used, not a fixed language.** This applies to chat answers, mock exams, and practice questions — the AI's output to the student should mirror the student's input language (English, Bulgarian, or otherwise), independent of the UI's English copy. A soft "respond in the same language as the question" instruction alone was unreliable with `minicpm-v` (confirmed: Bulgarian input answered in English), so `RAGService.cs` (`Ask`/`AskStreamAsync`), `ExamService.cs`, and `PracticeQuestionService.cs` first resolve the input's language via `LanguageDetectionService.cs` and, when resolved, name it explicitly (`"Respond entirely in Bulgarian."`) rather than leaving inference to the model; the original soft wording remains as the fallback when detection can't resolve a language. `ChatSessionService.cs`'s `GenerateTitleAsync` still uses the older soft-only wording and hasn't been revisited. When adding a new LLM-calling prompt that produces user-facing text, resolve the language via `LanguageDetectionService` and name it explicitly rather than assuming the model will infer it — see `DetectLanguageName`'s `requireStrongSignal` parameter below before trusting a short/bare input.
- **`LanguageDetectionService.DetectLanguageName(text, requireStrongSignal)` has a known reliability boundary.** Its n-gram detector is accurate on real sentences at any length (verified: short questions like "What is momentum?" detect correctly), but confidently *wrong* on bare, function-word-free noun phrases — e.g. "Algebra" misdetects as Afrikaans, "Quadratic Equations" as Italian, both at reported 100% confidence. Cyrillic script is always trusted directly (bypasses the n-gram model entirely) since this app's only Cyrillic curriculum language is Bulgarian and that check is reliable at any length. `ExamService` passes `requireStrongSignal: true` because `topic` is often a bare phrase — non-Cyrillic results are only trusted there when the input has ≥4 words, otherwise it falls back to the soft instruction (never regresses below pre-fix behavior). `RAGService`/`PracticeQuestionService` use the default (`false`) since their inputs are always full questions.
- **Known gap (as observed under `minicpm-v`): mock exam generation (`ExamService.GenerateExamAsync`) inconsistently produced English (or, once observed, Chinese) output for Bulgarian topics, even with the language correctly detected and explicitly named in the system prompt** — verified via server-side logging that the correct instruction reached the model every time; retesting the identical request repeatedly showed English, Chinese-drift, and partial-Bulgarian-with-English-scaffolding outputs, i.e. genuine stochastic model behavior, not a prompt-delivery bug. This looked like an inherent `minicpm-v` limitation on longer structured generation in a low-resource language, not something further prompt wording was likely to fix. `Llm:OllamaModel` has since been switched to `todorov/bggpt`, a Bulgarian-specialized model, specifically to address this; a single post-switch retest of both a live chat answer and a full mock exam (topic: "Ирационални числа") produced clean, sustained Bulgarian throughout with no English/Chinese drift. That's a positive signal but only one sample against documented *stochastic* failures — don't treat this gap as closed until it's been retested across multiple runs. Chat answers and practice-question generation were verified reliable for Bulgarian under `minicpm-v` already.
- **Known gap: `PracticeQuestionService.GenerateAsync` can silently return an empty list for Bulgarian input.** The model's JSON array response occasionally gets cut off before its closing `]` (observed only for Cyrillic output, not English — likely a token-cost side effect of Cyrillic needing more tokens per word); the existing catch-all in `GenerateAsync` swallows the resulting `JsonException` and returns `new List<string>()`, so this fails silently rather than surfacing an error. Not yet fixed.
- **Exception: internal classification labels stay Bulgarian.** `ChatLogService.cs`'s subject/topic classifier (used to tag chat messages for folder/metadata purposes) always produces its `subject`/`topic` output in Bulgarian — these are canonical Bulgarian curriculum subject names for internal categorization, not the AI's answer to the student, so this policy doesn't apply to them.
- **Curriculum source material stays Bulgarian regardless.** This policy governs response language, not the language of the textbook content retrieved from Qdrant — `RAGService.cs`'s existing "...may be in a different language — translate as needed" instruction already handles translating source excerpts into the answer.

## AI Answer Accuracy (`todorov/bggpt`)

- **Known gap: `todorov/bggpt` is noticeably weaker on multi-step physics word problems than on pure symbolic math**, based on a 2026-08-21 manual test of 10 hard (upper-high-school/early-olympiad level) problems sent directly to Ollama (bypassing RAG, so this reflects raw model capability, not retrieval quality). Math: 5/6 fully correct (trig equation solving, integration by parts, Taylor-series limit, combinatorics/probability) plus 1 with a correct calculus setup but a wrong final cube-root arithmetic step. Physics: only 1/4 fully correct (simple harmonic motion) — the other 3 had genuine conceptual errors, not just arithmetic slips:
  - Projectile motion: conflated "time to reach max height" with "total time of flight," halving the horizontal range.
  - Series-parallel circuit: incorrectly claimed parallel-connected resistors carry equal *current* (they share equal *voltage*, not current) and reported the wrong current through one branch.
  - Incline with friction: omitted the `cos(θ)` factor from the friction force (used `μmg` instead of `μmg·cos θ`) and let potential-energy terms wrongly cancel, giving a materially wrong final velocity.
  
  These errors were confidently formatted and easy to mistake for correct — a bigger risk for a tutoring product than an obviously garbled answer. Only one sample per problem was tested, so this isn't a rigorous benchmark, but it's a strong enough signal that **physics answers from this model should not be trusted without spot-checking**, especially anything involving force decomposition, circuit topology, or projectile/rotational kinematics. If physics curriculum ingestion is ever added (currently only `Database/DataPdf/Grade10/Math/` exists — see Directory Structure), this gap should be re-verified with RAG context included, and a stronger/larger model should be considered if physics tutoring becomes a priority.

## Retrieval Quality (`nomic-embed-text-v2-moe` + prefixes)

- **Methodology:** a retrieval audit (2026-08-26/27) built CLI-only measurement tooling (`ChunkSampler.cs`, `RetrievalFixtureModels.cs`, `RetrievalComparisonRunner.cs` — see Directory Structure) and a 20-question fixture (`TestData/RetrievalFixtures/grade10-math-v1.json`) to compare embedding configurations against the real ~920-chunk Grade 10 Math corpus, not a small synthetic sample. This is what led to the `nomic-embed-text` → `nomic-embed-text-v2-moe` + prefix switch documented in the Technology Stack table above. Post-migration, a direct measurement against the real, now-migrated `studyassist` collection (`compare-retrieval --current-prefix`) showed **3/20 → 13/20** questions with the correct chunk in the top 3 — a real, verified improvement, not just a projection.
- **Fixed 2026-08-31: formula-dense pages had corrupted Pix2Text math-OCR output.** Confirmed via `show-chunk` on the chunks behind fixture questions q02/q03/q19/q20 (`5StereometryArhimed.pdf` pp.21, 44, 47): truncated LaTeX commands mid-token (e.g. `{\fra` instead of `{\frac`) and Cyrillic figure-labels/subscripts misrecognized as garbled spaced-out Latin letters (e.g. "BHcoцHHaTa Ha HpH3MaTa" ≈ mangled "височината на призмата", "the height of the prism"). Root cause, confirmed by reading `MathOcrService.cs` and `pix2text_server.py` directly: (1) `pix2text_server.py`'s `is_suspect_formula` filter — meant to catch exactly this kind of garbled output — only flagged content when `inner.isalpha()`, so a garbled word containing a digit-homoglyph for a Cyrillic letter (e.g. the literal `3` standing in for "З" in "HpH3MaTa") slipped through; now uses `isalnum()` plus an explicit at-least-one-letter check instead. (2) `PDFLoader.GetPageImages`'s shared 96 DPI default left little detail for Pix2Text's LatexOCR to work with on small subscripts/dense formula clusters; the formula-OCR call site (`LoadTextWithSelectiveFormulaOcrAsync`) now passes `dpi: 200` explicitly, without changing the shared default other callers (the vision-OCR fallback) still rely on. Both fixes were verified live against the running Pix2Text server *before* touching production — a known-garbled formula on a real page disappeared across 3 repeat OCR calls at 200 DPI with no measurable inference-time cost (~77-81s either way) — then confirmed clean on the actual pp.21/44/47 chunks after a production `reingest-grade`.
- **Partially addressed 2026-08-31: the fixture's one-expected-chunk-per-question design can undercount real system quality.** `FixtureQuestion.RequireAll` (see `RetrievalFixtureModels.cs`) already supported crediting an alternate chunk as a pass (`false` = any one of several `ExpectedChunks` counts, not just multi-hop's original "all must match" use) — it just wasn't exercised that way yet. Live spot-checks via `diagnose-retrieval --prefix` on fixture questions scored as "misses" (q01, q02, q16) showed each needs a real correctness judgment, not a blind rank-1 credit: **q16** ("Как се намира x-координатата на върха на парабола?") — a different chunk on the same page, containing "връх на параболата", ranks #1 and genuinely answers the question in prose, so it's now added as a second `expectedChunks` entry with `requireAll: false`; confirmed via `compare-retrieval --current-prefix` that q16 now passes (production-prefixed aggregate: 13/20 → **14/20**). **q01/q02**'s top-ranked alternates were checked and are only topically related (a sphere-definition page, cone/pyramid surface-area chunks) — not actually correct answers — so those two remain single-chunk, `requireAll: true`, and their "miss" status is legitimate, not a fixture defect.
- **Fixed 2026-08-31 (root cause was misdiagnosed earlier — corrected here): some pages produced several near-duplicate chunks.** This was originally attributed to stale data from pre-`reingest-grade`-era manual ingestion and described as "byte-identical" — both wrong. A from-scratch `reingest-grade` (after confirming, via an isolated temp-collection test, that `QdrantService.DeleteFileAsync`'s filter reliably purges a file's old points first) reproduced the same near-duplicate pattern immediately, proving it wasn't leftover data. The chunks were also never byte-identical — full-text diffs (not just the truncated preview `sample-chunks` shows) confirmed each had different length and content, sharing only a common leading substring. Real root cause: a bug in `PDFLoader.ChunkText`'s sentence-overlap fallback (`GetLastSentences`) — see the `PDFLoader.cs` entry in Directory Structure above for the mechanism and fix. Verified end-to-end: the worst offender (`1IrationalArhimed copy.pdf` p.10) went from 12 near-duplicate chunks (pre-fix) → 8 (after an initial word-count-based fallback, still insufficient for text with very few space-delimited tokens) → a handful of short, non-propagating overlaps after the final character-capped fallback. The character-cap fix landed in code after the second production `reingest-grade` already ran, so the *live* collection reflects the word-count-fallback intermediate state, not the final fix — a future `reingest-grade` will pick up the character-cap version automatically. `RetrievalComparisonRunner`'s `--full-corpus` mode's in-code comment about duplicate chunks and point-id matching should be read with this corrected understanding.

## Definition of Done

A feature is complete when all of the following are true:

1. Service method returns a typed result — no `object` returns, no unhandled exceptions for expected failure cases
2. Controller endpoint exists with the correct HTTP method, route, auth requirements, and status codes
3. Rate limiting and `[Authorize]` guards are applied where the feature requires them
4. A manual end-to-end test passes against a running local instance (login → use the feature → confirm result)
5. No new `.Result` / `.Wait()` calls or raw SQL outside `RateLimiter.cs` were introduced
